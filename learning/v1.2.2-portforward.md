# Issue Summary: Port Forwarding "Connection Refused" & "Empty Response" (v1.2.2)

## The Problem
Users experienced "Connection Refused" or "Empty Response" errors when attempting to port forward services (specifically `aspire-dashboard` on port 8088 and `kafka-ui`). While `kubectl port-forward` worked correctly, the internal `KubeTools4Dev` implementation failed.

## Root Causes & Solutions

### 1. Localhost Binding (IPv4 vs IPv6)
*   **Issue**: The application was binding to `IPAddress.Any` (IPv4) or `IPAddress.IPv6Any`. Modern operating systems and browsers often prioritize IPv6 (`::1`) for "localhost". If the listener only bound to IPv4 (`127.0.0.1`), connections via `localhost` could fail with **Connection Refused**.
*   **Fix**: Modified the listener logic to explicitly mimic `kubectl` behavior by starting **two concurrent listeners**:
    *   One bound explicitly to `IPAddress.Loopback` (`127.0.0.1`).
    *   One bound explicitly to `IPAddress.IPv6Loopback` (`::1`).

### 2. Service-to-Pod Port Mismatch
*   **Issue**: Users typically select the **Service Port** (e.g., 8088) to forward. The previous implementation attempted to connect to this same port `8088` on the Pod. However, Services often map the external port to a different **Target Port** on the container (e.g., `8088` -> `18888`). Connecting to 8088 on the Pod failed because nothing was listening there.
*   **Fix**: Implemented **Port Resolution Logic**. The application now:
    1.  Fetches the `Service` definition.
    2.  Finds the matching `ServicePort` entry.
    3.  Reads the `TargetPort`.
    4.  Forwards traffic to the resolved `TargetPort` on the Pod, not the input Service Port.

### 3. Named Ports (Format Exception)
*   **Issue**: Some services (like `kafka-ui`) use **named ports** (strings like `"http"`) in their Service definition instead of numbers. The application crashed with a `FormatException` when attempting to parse `"http"` as an integer.
*   **Fix**: Updated the resolution logic to handle `IntOrString` target ports:
    *   If the target port is an integer, use it.
    *   If the target port is a string, look up the **Pod Spec**, find the container port with that `Name`, and use its resolved port number.

### 4. Silent Failures (Error Channel)
*   **Issue**: When the Pod refused a connection (e.g., due to port mismatch), the error was written to the Kubernetes Port Forward **Error Channel (Stream 1)**. The application was ignoring this stream, leading to silent "Empty Response" failures.
*   **Fix**: Added a background task to actively read Stream 1 and log any output as an Error. This provided critical diagnostics (e.g., explicit "Connection refused" messages from the Pod).
